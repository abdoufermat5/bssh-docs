You need Bayesian SSH 2.13 or later, a few hosts saved in `bssh`, and an agent that speaks MCP.

<Aside type="caution" title="Agents can't type passwords">
An agent runs `bssh ai mcp` with no terminal, so bssh never prompts during an agent run. Use key, ssh-agent or Kerberos (with a ticket from `kinit`) for the hosts you want agents on. A host that needs a password, a passphrase or a one-time code fails with a clear error instead of hanging.
</Aside>

## Connect your agent

<Steps>

1. Add bssh to your agent's MCP configuration:

   ```sh
   bssh ai install claude-code
   ```

   The same command works with `codex`, `cursor`, `vscode`, `claude-desktop` and `omp`. It adds one entry named `bssh` and leaves everything else in the file alone, after a backup. `--dry-run` prints the change without writing it:

   ```json title="~/.claude.json"
   {
     "mcpServers": {
       "bssh": {
         "type": "stdio",
         "command": "/usr/bin/bssh",
         "args": ["ai", "mcp", "--policy", "default", "--env", "default"]
       }
     }
   }
   ```

   The entry is pinned to the environment that was active when you installed it, so switching environments with `bssh env use` does not silently change which hosts and policy the agent gets. For Codex, bssh also writes `tool_timeout_sec` to the approval window plus 30 seconds; Codex's own default would give up on a tool call before a person could answer.

   Any other MCP client works too: point it at `bssh ai mcp` over stdio.

2. Restart the agent. It now has the bssh tools, starting with `list_hosts`; with the observe profile, the tools that change a host are not even listed. The install command prints the same next steps, and what the policy it wrote allows.

3. Ask it something about a host:

   > Why is nginx returning 502 on web-1?

   A typical session: `list_hosts`, `observe` for the failed units, `search_logs` on the nginx journal, `read_file` on the site configuration. None of it asks you anything, because none of it can change the host.

</Steps>

<Aside type="tip" title="Hosts behind a bastion">
Jump hosts, OVH-style Kerberos bastions and a `ProxyJump` set only in `~/.ssh/config` all work without a prompt on any hop; each has its own limits for certificates. See [Bastions and jump hosts](/ai/bastions/).
</Aside>

## What the agent may do at first

Until you write a policy, bssh uses the built-in **observe** profile on every host you have saved: the agent can read, and every write is refused. It acts for you, so it sees the hosts you already have, never more.

Check how a command would be treated, here or at any time:

```text frame="terminal"
$ bssh ai explain --host web-1 "journalctl -u nginx --since '10 min ago' | grep -i error"
command: journalctl -u nginx --since '10 min ago' | grep -i error
tags:    read
commands:
  1. journalctl -u nginx --since 10 min ago
     tags:     read
     rule:     journalctl read
  2. grep -i error
     tags:     read
     rule:     grep
policy:  default  host: web-1
decision: allow - analyzer: every command is read-only
```

## Let it fix things

Give the `default` policy the **operate** profile and a scope:

```sh
bssh ai policy set default --profile operate --tag staging --tag prod
```

Or write the policy by hand under `ai.policies` in your configuration file, `~/.config/bayesian-ssh/environments/default/config.json`, when you also want approval rules and write paths:

```json
"ai": {
  "policies": {
    "default": {
      "profile": "operate",
      "scope": { "tags": ["staging", "prod"] },
      "approval": { "in_client": ["staging"], "two_person": ["prod"] },
      "write_paths": ["/etc/nginx/**"]
    }
  }
}
```

Now the agent can propose changes on hosts tagged `staging` or `prod`, and edit files under `/etc/nginx`. Every change asks first. On `staging`, a low-risk change can be confirmed in the agent's own client; anything else goes to the desktop app or the terminal. See [Policies](/ai/policies/) for every field.

## Approve the first change

Ask the agent to fix what it found. It sends a change plan: the steps, the diff, how to check the fix and how to undo it. Keep the desktop app open on its AI section, or follow the run in another terminal:

```sh
bssh ai watch
```

`bssh ai watch` shows each call and each decision as it happens, and pops up the request with `a` to approve and `d` to deny. `bssh ai approve` does the same for one request (add `--follow` to keep answering), and `bssh ai approve --deny --reason "…"` refuses with a reason the agent receives. Once approved, bssh runs exactly the approved steps, then the plan's verify steps, and the agent reports back.

## See what happened

```sh
bssh ai log                  # recent runs
bssh ai log <run> --report   # hosts touched, changes with diffs, approvals, undo points
bssh ai status               # running agents, pending approvals, active grants
bssh ai stop                 # end a run now
```

Everything above also sits in a signed, hash-chained log on your machine.

## Keep agents on the bssh path

An agent that also has a shell tool can still try plain `ssh`. For Claude Code, bssh can install a hook that blocks `ssh`, `scp`, `sftp` and `rsync` to the hosts bssh knows and points the agent to the bssh tools instead:

```sh
bssh ai install claude-code --guard
```
